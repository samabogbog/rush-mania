# การตรวจอาการสะดุดออนไลน์

ปัญหาที่ทำซ้ำได้: เซิร์ฟเวอร์เดิมตรวจ input เก่ากว่า 500 ms ที่เวลารับคำขอ และทิ้ง input นั้นตลอดช่วง catch-up เมื่อรอบ HTTP ช้ากว่า 500 ms จึงไม่เดินเลย แม้ API ตอบ 200 ฝั่งลูกข่ายเคยจำกัดการคาดการณ์ตำแหน่งที่ 1.6 หน่วยและดึงกลับไป snapshot ทำให้เกิดจังหวะหยุด/ดึงกลับ

การแก้:

- เซิร์ฟเวอร์ใช้ input lease 1500 ms และตรวจหมดอายุตามเวลาในแต่ละ simulation step โดยยังจำกัด catch-up ไม่เกิน 0.5 วินาที ปล่อยปุ่มแล้วส่ง zero input; หลุดนานแล้วไม่เดินหรือฟาร์มชดเชยเวลาออฟไลน์
- ตัวละครหลักคาดการณ์เฉพาะตำแหน่งสำหรับวาดภาพ และเกลี่ยความคลาดเคลื่อนจาก snapshot ตรวจสิ่งกีดขวาง ขอบแผนที่ ตาย และ pause ไม่คำนวณรางวัลหรือดาเมจในลูกข่าย
- มอนสเตอร์และผู้เล่นอื่นเก็บ snapshot หลายรายการเพื่อ interpolate และ extrapolate แบบจำกัด เมื่อไม่มีข้อมูลใหม่จะหยุด ไม่ลากตำแหน่งต่อไม่สิ้นสุด รีเซ็ตเมื่อเปลี่ยนแผนที่ เกิดใหม่ ตาย ย้ายตำแหน่งไกล หรือ entity หาย
- เวลาแอนิเมชันสำหรับภาพลดลงทุกเฟรมโดยไม่เปลี่ยน cast/cooldown ของเซิร์ฟเวอร์
- `window.mossvale.snapshot().network` แสดง RTT, รอบ snapshot, อายุ snapshot, ขนาด response, interpolation delay, จำนวน buffer และคำสั่งค้าง

หลักฐานก่อนแก้: Chromium/Playwright ผ่าน HTTP API จริงในเครื่อง ฉากโหลด GLB ครบ modelErrors=0 จำลองหน่วง response เพิ่ม 700 ms; API 200 ทุกคำขอ RTT ราว 724–904 ms กด D ~4.7 วินาทีตำแหน่ง authoritative ไม่ขยับ เทียบ delay250 ms ซึ่งเดินได้ ใช้ checkout commit 9fb4a35 แยกสำหรับ baseline และ SQLite ชั่วคราว ไม่แตะผู้เล่นจริง

ผลตรวจรอบแรกหลังแก้: delay700 ms เดิน authoritative 6.6 หน่วยในช่วงเก็บตัวอย่าง ~4.6 วินาที ไม่มี page error แต่พบการดึงภาพกลับบางจังหวะ จึงเพิ่ม regression test และปรับ correction เพิ่มก่อนส่งมอบ

ผลตรวจรุ่นสุดท้าย: correction ที่สวนทาง input ขณะกดเดินจำกัดไม่เกินครึ่งหนึ่งของระยะเดินในเฟรมนั้น เก็บ correction ที่เหลือไว้และเกลี่ยเมื่อปล่อยปุ่ม Buffer ปรับตามรอบรับข้อมูลและ jitter สูงสุด 900 ms มี playback time ที่ไม่ย้อนกลับ เก็บสูงสุด 8 snapshots ต่อ entity, extrapolate สูงสุด 100 ms / 0.5 หน่วย, หยุดคาดการณ์ตัวละครเมื่อ snapshot เก่าถึง 1200 ms

ทดสอบ Playwright ครั้งสุดท้าย delay700 ms: authoritative เดิน 8.8 หน่วยในช่วงเก็บตัวอย่าง ~4.57 วินาที, ไม่พบ reverse frame ระหว่างกด D, ไม่มี page error และ API 200 ทุกคำขอ; delay250 ms: authoritative เดิน ~16.69 หน่วยใน ~4.53 วินาที ไม่มี page error รายงาน/ภาพเก็บส่วนตัวใน `.local/final-{700,250}.{json,png}` ผลตัวเลขนี้ใช้แสดง regression และข้อจำกัดเท่านั้น ไม่ใช่ benchmark ระยะเดินปกติ เพราะเฟรมทดสอบใช้ software renderer และเกมจำกัด dt แต่ละเฟรม

Build ผ่านและชุดทดสอบ 32 ข้อผ่าน ครอบคลุม latency, prediction/interpolation, stale input, auth, server authority, CAS, ธุรกรรมและ Vercel native ESM entry points

ข้อจำกัด: เบราว์เซอร์ทดสอบใช้ SwiftShader บน CPU; ไม่ใช้ FPS หรือระยะภาพต่อเฟรมเป็นผลเครื่องผู้เล่น และไม่อ้างว่าได้ควบคุมแท็บ Codex ของผู้ใช้ เบราว์เซอร์ทดสอบเข้าโดเมน Vercel จริงติด ERR_TUNNEL_CONNECTION_FAILED; ผลฉากเป็น localhost ที่จำลอง network delay การตรวจ Vercel หลัง deploy ใช้ปลั๊กอินตรวจ SHA และ API แยกต่างหาก

นี่เป็นการแก้ระบบ HTTP ปัจจุบัน ยังไม่ได้เปลี่ยนเป็น WebSocket หาก RTT ต่อเนื่องเกิน 0.5 วินาที simulation cap ยังทำให้เกมช้าลงได้ และ buffer ภาพที่เพิ่มขึ้นแลกกับความหน่วงในการเห็นผู้เล่น/มอนสเตอร์

สำหรับระบบระยะถัดไป: ย้าย simulation ไปเซิร์ฟเวอร์เกมที่รันต่อเนื่อง tick คงที่ (เช่น 20 Hz), รับ input ผ่าน WebSocket พร้อม sequence/ack, ลูกข่าย replay input ที่ยังไม่ได้รับ ack แล้ว reconcile, ส่งเฉพาะสถานะที่เปลี่ยนและใกล้ตัวผู้เล่น, เก็บ state ใน memory และเซฟลง Turso เป็นระยะพร้อม transaction สำหรับเงิน/ไอเท็ม Vercel ใช้เสิร์ฟ frontend และ auth ต่อได้ แต่ Functions ปัจจุบันไม่ใช่เซิร์ฟเวอร์เกมที่ถือการเชื่อมต่อถาวร
