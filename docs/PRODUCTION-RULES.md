# กติกาการผลิตงานภาพ Mossvale

## เป้าหมายและขอบเขต

ผู้เล่นให้คุณภาพปัจจุบัน 5/10 เป้าหมายรอบนี้คือ 8–9/10 สำหรับ **งานภาพ ตัวละคร ฉาก การเคลื่อนไหว สกิล และไอคอน** ตัวเลขนี้ไม่ใช่การรับรองว่า MMORPG ทั้งเกมพร้อมเปิดบริการ: เครือข่าย เศรษฐกิจ เนื้อหา ความปลอดภัย และการดูแลหลังเปิดต้องผ่านเกณฑ์ต่างหาก

ผู้ควบคุมการผลิตประเมิน วางข้อกำหนด มอบหมาย ตรวจหลักฐาน และอนุมัติการส่งมอบ ไม่ลงมือแก้ runtime เอง ผู้ปฏิบัติใช้ GPT-6.1 Sol ระดับ reasoning low ตามคำขอ Sol Light แยกหน้าที่และความเป็นเจ้าของไฟล์ชัดเจน

## บทบาทและการทำงานร่วมกัน

- Icon artist: ออกแบบ PNG สกิลครบ 60 ภาพ บอกทักษะได้จากรูป สีสด ขนาดวัตถุและพื้นที่ขอบสม่ำเสมอ ทั้งภาพใหญ่และขนาด hotbar จริง
- Character artist/animator: ตัวละครและมอนสเตอร์ชิบิโค้งมน สัดส่วนและวัสดุร่วมกัน มี anticipation, weight shift, follow-through และ locomotion ที่สัมพันธ์ความเร็ว
- Environment artist: ภูมิประเทศ ต้นไม้ สิ่งก่อสร้าง แสงและวัสดุ มีจุดสนใจ ภาพระยะเล่นอ่านง่าย และ collision ตรงกับสิ่งที่เห็น
- Combat/VFX specialist: ท่าร่ายและโจมตีเฉพาะสกิล ลำดับเตรียม–ออกผล–คืนท่า ระดับสูงมีพัฒนาการ อ่านผลการโจมตีได้ และจำกัด effect cost
- QA/governance: ดูแลเอกสาร ทดสอบ ถ่ายหลักฐาน และเสนอคะแนนโดยไม่แก้ runtime; ผู้ควบคุมตัดสินคุณภาพจริงอีกครั้ง

แต่ละคนแก้เฉพาะพื้นที่ที่รับผิดชอบ หากต้องแตะไฟล์ร่วมให้แจ้งเจ้าของและตกลง integration ก่อน ห้ามเปลี่ยน schema เซฟ กติกาดาเมจ server authority หรือบัญชีผู้เล่นเพื่อทำ demo งานภาพ ห้ามรัน build หรือ browser QA ระหว่างเจ้าของ runtime ยังแก้ไฟล์: แจ้ง QA ว่าพร้อม แล้วหยุดแก้จนจบการตรวจ

## การตรวจรับและแก้ซ้ำ

1. ส่งมอบพร้อมรายชื่อไฟล์ หลักฐานภาพ/วิดีโอ วิธีทดสอบ ที่มาของ assets และข้อจำกัดที่ยังมีจริง
2. QA ตรวจเล่นได้ input เมนู จังหวะสกิล เซฟเดิม server-authoritative commands และ low/high graphics
3. บันทึก FPS/เฟรม p50/p95, draw calls, mesh/effect count เทียบ idle กับ combat burst ตรวจ effect/material disposal และ bounded allocations
4. เป้าหมายเครื่องจริง desktop 60 FPS, low-end/mobile 30 FPS; headless SwiftShader เป็น software renderer ใช้ตรวจความถูกต้องและเปรียบเทียบภายในเครื่องเดียวกัน **ห้ามอ้างว่าเป็นผล FPS เครื่องผู้เล่น** ต้องรายงานสภาพแวดล้อม
5. ผู้ควบคุมเปิดหลักฐานและให้คะแนนแยกส่วน ถ้าไม่ผ่าน ส่งข้อบกพร่อง concrete พร้อมภาพ/เวลาในคลิปกลับเจ้าของเดิม แล้วตรวจซ้ำจนผ่านหรือระบุ blocker จริง
6. เผยแพร่หลังอนุมัติคุณภาพเท่านั้น โดยรักษาการเข้าถึงไซต์และฐานข้อมูลเดิม ส่งมอบ source และหลักฐานที่ตรวจได้

ห้ามส่ง placeholder, แอบลด resolution/เอฟเฟกต์จนภาพเสียเพื่อผ่าน performance, หรือลบเนื้อหาเดิมเพื่อให้ test ผ่าน ถ้าข้อจำกัดของ asset/tool ทำให้คุณภาพไม่ถึง ให้รายงานตรงไปตรงมาและเสนอทางแก้ก่อนตีตราว่างานเสร็จ

## กติกาหลักฐาน QA

อ่าน mapping input จาก source จริงก่อนบันทึก ไม่เดาปุ่มควบคุม ทุกกริยาที่อ้างว่าทดสอบต้องยืนยันผลที่สังเกตได้ เช่น เดินแล้ว x/z เปลี่ยน เลือกเป้าหมายแล้ว target เปลี่ยน ร่ายแล้ว cast/MP/cooldown เปลี่ยน และโจมตีแล้ว HP หรือ kill เปลี่ยน การกดปุ่มแล้วรออย่างเดียวไม่ถือว่าครอบคลุมพฤติกรรมนั้น

ภาพฉากต้องรอ GLB ของตัวละครและมอนสเตอร์ในพื้นที่โหลดครบ ตรวจ modelErrors = 0 และตรวจภาพจริง แยก render-only preview ออกจากสกิลที่เรียนและร่ายผ่านกติกาเกมจริงอย่างชัดเจน ห้ามรวมจำนวน test เก่าก่อนแก้ runtime รอบล่าสุดเป็นผลตรวจรับ build สุดท้าย

ก่อน browser/API QA ตรวจ server readiness (หน้าเว็บและ API ตอบจริง) และให้เจ้าของไฟล์ runtime หยุดแก้ระหว่างบันทึก HMR ที่ทำให้ context เปลี่ยน หรือ localhost port ปิด เป็นปัญหาของ fixture/การประสานงาน ต้องแก้และตรวจใหม่ ไม่ตีความเป็นบั๊กของเกมและไม่ใช้คลิปที่เสียเป็นหลักฐานคุณภาพ ตรวจ page error แบบหยุดทันทีและรอโหลดแบบมีเวลาเพดาน
