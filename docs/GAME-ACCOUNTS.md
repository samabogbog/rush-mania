# Game accounts

Online play now requires a game username/password account. Sites keeps the site's existing access restrictions; it does not automatically sign the player into the game. Device practice remains at `?practice=1`. Local development defaults to the login screen and needs both Vite and `npm run dev:server`.

Usernames are case-insensitive ASCII letters, numbers and underscores, 3–24 characters. Passwords are 10–128 characters, hashed using WebCrypto PBKDF2-SHA256 with 100,000 iterations and independent random 256-bit salts. No plaintext password is stored. Password recovery and password changes are not available yet.

Registration binds the first account for a trusted Sites identity to that identity's existing character ID. The database enforces a unique legacy binding; subsequent accounts get independent random character IDs. Concurrent claims cannot inherit the same character. If a competing registration claims the binding first, the request may return a retry message. Admin game privileges require both the trusted Sites owner email and its bound account; arbitrary usernames do not grant admin access. Operator APIs remain restricted to the trusted owner identity.

Sessions use random 256-bit bearer cookies, with only SHA-256 token hashes persisted. Cookies are HttpOnly, SameSite=Strict, Secure over HTTPS, and expire after seven days. Login replaces the session presented on that device; logout deletes it server-side. Other devices keep their sessions. An expired/revoked game session returns to the account screen. Account mutations require an exact matching Origin. Login and registration share a persistent limit of 20 attempts per ten-minute window per username and trusted IP/identity. Expired limiter rows are removed during subsequent attempts.

Apply every SQL migration under `drizzle` before deploying the Worker. The local SQLite adapter applies them automatically and stores accounts and sessions in the same durable database as characters. Sites uses the same prepared statements with D1. Back up the full SQLite/D1 database for account recovery: existing in-game realm backups contain world state only, not accounts or sessions.

These cover salted hashing, session cookies, login failure, logout and expiry, account separation, unique legacy claims, Origin rejection, rate limiting and existing game authority/operator behavior.
